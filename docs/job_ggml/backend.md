# Backends

The JOB GGML backend subsystem wraps the execution, memory, scheduling, and graph-management interfaces provided by GGML backends.

Backend objects are separate from device objects. Devices describe and expose available compute hardware, while backend objects represent the execution and memory resources used to run work on those devices.

## JobGgmlBackend

`JobGgmlBackend` is the owning JOB wrapper for an initialized GGML backend. A backend represents an active execution context for a device and provides the operations used to transfer tensor data, execute computation graphs, create graph plans, and synchronize backend work.

Construction takes ownership of either a native `ggml_backend_t` or a moved `ggml_backend_ptr`. The wrapper retains the backend name and exposes both the native backend handle and the native GGML device associated with it. A borrowed `JobGgmlDevice` association may also be exposed when the backend has been linked to its higher-level device wrapper.

Tensor data may be transferred asynchronously between host storage and backend tensors through one-dimensional and strided two-dimensional transfer helpers. Tensor data may also be copied asynchronously between different `JobGgmlBackend` instances. `synchronize()` waits for outstanding backend work to complete.

Computation graphs may be executed directly through synchronous or asynchronous graph execution. For repeated execution, `createGraphPlan()` builds an owning `JobGgmlBackendGraphPlan` tied to the backend, and `computeGraphPlan()` executes that plan only when it belongs to the same backend.

Backend events integrate asynchronous execution with `JobGgmlBackendEvent`. Events may be recorded on the backend and later waited on, providing explicit synchronization between backend operations without exposing the native GGML event API directly.

`isValid()` reports whether the wrapper currently owns a native backend, while `isCpu()` determines whether the native device associated with that backend is a CPU device.


## JobGgmlBackendSched

`JobGgmlBackendSched` is the JOB wrapper for the GGML backend scheduler. It coordinates one or more `JobGgmlBackend` instances and provides the graph allocation, backend assignment, graph splitting, and execution facilities required for computations that may span multiple execution backends.

A scheduler is constructed from at least one backend together with an optional matching collection of `JobGgmlBackendBufferType` objects. When buffer types are not supplied explicitly, GGML selects the appropriate type for each backend and JOB retains wrappers for the resulting buffer types. Scheduler configuration also includes the maximum graph size, parallel execution mode, and operation-offload behavior.

The scheduler exposes its participating backends and their associated buffer types and allocation sizes. It also reports the number of graph splits and copies generated by GGML, allowing callers to inspect how a graph has been partitioned across the available execution resources.

Graph memory can be measured and reserved before execution. Individual tensors may be assigned to specific backends, after which a graph can be split according to those assignments and the capabilities of the configured backends. Graph storage may then be allocated through the scheduler before computation begins.

Graphs can be executed synchronously or asynchronously through the scheduler. `synchronize()` waits for outstanding scheduled work, while `reset()` clears scheduler execution state so the scheduler can be reused.

`JobGgmlBackendSched` also supports an evaluation callback using `std::function`. The callback receives a temporary `JobGgmlTensor` view for the tensor currently being evaluated together with GGML's `ask` state. C++ exceptions are contained at the native callback boundary and cause evaluation to stop rather than being allowed to cross into the C API.

Tensor/backend associations are restricted to backends owned by the scheduler. This preserves the scheduler's internal backend topology and prevents tensors from being assigned to unrelated backend instances.

## JobGgmlBackendReg

`JobGgmlBackendReg` is the JOB wrapper for a GGML backend registry. It represents a registered backend implementation and provides access to the devices and procedures exposed by that registry.

The native `ggml_backend_reg_t` is borrowed from the GGML registry and is not owned by `JobGgmlBackendReg`. The wrapper retains the registry name and exposes the number of devices registered by the backend.

Devices may be accessed by index through `device()`, which returns the native `ggml_backend_dev_t` reported by the registry. Higher-level device wrapping and ownership are handled by the device subsystem rather than by `JobGgmlBackendReg`.

Backend-specific procedures may also be queried by name through `procAddress()`. This provides access to optional or implementation-specific entry points exposed by the native GGML backend registry without making them part of the generic JOB backend interface.

The underlying native registry handle remains available through `backendReg()`, while `isValid()` reports whether the wrapper references a valid GGML backend registry.

## JobGgmlBackendBufferType

`JobGgmlBackendBufferType` represents a GGML backend buffer type and the allocation characteristics associated with it. The native `ggml_backend_buffer_type_t` is borrowed from GGML, while JOB retains the descriptive information needed to reason about allocations through the C++ interface.

A buffer type exposes its name, required memory alignment, maximum supported allocation size, and whether the memory it represents is host-accessible. It also retains the native device associated with the buffer type when one is available.

Concrete backend buffers may be allocated directly from a `JobGgmlBackendBufferType` through `allocateBuffer()`. The wrapper also exposes allocation-size queries for both native `ggml_tensor` objects and `JobGgmlTensor` wrappers, allowing callers to determine how much backend memory a tensor requires before allocating it.

`isValid()` reports whether the wrapper references a valid native GGML buffer type. The underlying `ggml_backend_buffer_type_t` and associated `ggml_backend_dev_t` remain available when lower-level interoperability is required.


## JobGgmlBackendBuffer

`JobGgmlBackendBuffer` is the owning JOB wrapper for a concrete GGML backend buffer. It represents an actual memory allocation created for a backend rather than the allocation policy described by `JobGgmlBackendBufferType`.

Construction takes ownership of either a native `ggml_backend_buffer_t` or a moved `ggml_backend_buffer_ptr`. The native buffer is retained through GGML's RAII wrapper and is released with the JOB object.

A backend buffer exposes its name, native buffer and buffer type, host-memory status, base address, allocation size, alignment requirements, and maximum supported tensor size. Allocation-size queries are available for both native `ggml_tensor` objects and `JobGgmlTensor` wrappers.

Tensors may be initialized against the buffer through `initializeTensor()`, allowing the backend-specific buffer implementation to prepare tensor storage before execution.

The buffer also tracks its `JobGgmlBackendBufferUsage`, which can be queried or changed through the JOB enum interface. Native and JOB buffer-usage values can be converted directly through the provided mapping helpers.

Buffer contents may be cleared to a selected byte value, while `reset()` releases the owned native buffer and returns the wrapper to an empty state. `isValid()` reports whether an owned native backend buffer is currently present.


## JobGgmlBackendEvent

`JobGgmlBackendEvent` is the owning JOB wrapper for a GGML backend event. Backend events provide a synchronization primitive associated with a backend device and are used to wait for device-side work to complete.

An event may be created directly from a native `ggml_backend_dev_t`, in which case JOB requests a new event from GGML, or constructed by taking ownership of an existing native event. Both raw `ggml_backend_event_t` handles and moved `ggml_backend_event_ptr` objects are supported.

The wrapper owns the native event for its lifetime and exposes it through `event()` when lower-level interoperability is required. `isValid()` reports whether a native event is currently owned.

Calling `synchronize()` blocks until the work associated with the event has completed. Synchronization is forwarded directly to the native GGML backend event.

## JobGgmlBackendBufferView

`JobGgmlBackendBufferView` provides non-owning access to a native GGML backend buffer whose lifetime is controlled by another GGML object.

The class exists for cases where wrapping the native buffer in `JobGgmlBackendBuffer` would create an incorrect second owner. The immediate example is `JobGgmlBackendGraphCopy`, whose native graph-copy aggregate owns a backend buffer together with its contexts and graph and releases them as a single unit.

`JobGgmlBackendBufferView` borrows the supplied `ggml_backend_buffer_t` and never releases it. The native owner must therefore outlive every view created for that buffer.

Despite being non-owning, the view exposes the same core inspection vocabulary used by owning backend buffers. Callers can inspect the buffer name and type, determine whether it represents host memory, access its base address and size, query alignment and maximum tensor size, determine tensor allocation requirements, and inspect the current buffer usage.

Operations that would imply ownership or mutation of the buffer lifetime are intentionally absent. The class is therefore suitable for inspecting externally owned backend memory without interfering with the native object's ownership model.


## JobGgmlBackendGraphCopy

`JobGgmlBackendGraphCopy` owns a GGML graph copy created for a specific `JobGgmlBackend`. The native `ggml_backend_graph_copy` aggregate contains a backend buffer, an allocated context, an unallocated context, and the copied computation graph.

Construction requires both a valid backend and a valid `JobGgmlCGraph`. The graph is copied to the requested backend through GGML and is considered valid only when all four native members of the resulting aggregate are present.

The graph-copy aggregate has a single ownership boundary. Its buffer, contexts, and graph are released together through `ggml_backend_graph_copy_free()`. They must not be placed into JOB wrappers that would independently release the same native objects.

For this reason, the contained buffer is exposed through `JobGgmlBackendBufferView`, and the two contexts are exposed through `JobGgmlContextView`. These wrappers borrow their native objects and never release them. The graph may likewise be accessed through `graphObject()` or through the native graph pointer exposed by `graph()`.

The graph copy also exposes direct access to its native buffer, allocated and unallocated contexts, computation graph, and complete `ggml_backend_graph_copy` structure when lower-level interoperability is required.

`reset()` releases the complete native graph-copy aggregate and clears the object. The destructor performs the same cleanup automatically.


## JobGgmlBackendGraphPlan

`JobGgmlBackendGraphPlan` is the owning JOB wrapper for a native GGML backend graph plan. Graph plans are created for a specific `JobGgmlBackend` and may be reused for repeated execution of a prepared computation graph.

The native `ggml_backend_graph_plan_t` is owned by the wrapper, while the originating `JobGgmlBackend` is borrowed. The backend must outlive the graph plan because GGML requires the same backend when the native plan is released.

A graph plan is valid only while both the borrowed backend and owned native plan remain valid. The originating backend can be inspected through `backend()`, and the native plan handle remains available through `plan()` for lower-level interoperability.

`reset()` releases the owned native graph plan through the originating backend and clears the plan state. The destructor performs the same cleanup automatically.
